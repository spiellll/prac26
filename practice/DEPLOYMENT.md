# Публикация дневника Ритм

## Один сайт и один сервер

Интерфейс собирается из существующих React-компонентов в статические файлы.
Flask обслуживает страницу `/`, картинки и API с одного адреса. На сервере
не нужен запущенный Node.js: он используется только на этапе сборки.
Gunicorn запускает Python-приложение. Docker собирает обе части автоматически.

## Render для демонстрации практики

В репозитории подготовлен `render.yaml`. Выберите эту ветку репозитория
в Render как Blueprint. Для Docker build context укажите папку проекта:
если он находится в подпапке `ritm`, root directory — `ritm`.
Для Blueprint в этой подпапке путь — `ritm/render.yaml`.

Конфигурация задаёт бесплатные web service и PostgreSQL. Актуальные
ограничения и условия показываются в Render перед созданием сервисов:
https://render.com/docs/free

Бесплатный web service имеет временную файловую систему, поэтому обычная
SQLite внутри контейнера потеряет изменения при пересоздании. В Blueprint
используется отдельная PostgreSQL. Бесплатная PostgreSQL Render истекает
через 30 дней; такая конфигурация подходит для краткой демонстрации,
но для постоянного личного дневника потребуется хранилище без этого срока.
Переход на платные услуги выполняется только после выбора владельцем аккаунта.

Настройки:

- `PUBLIC_DEMO=1`: у каждого браузера свой дневник через подписанную cookie.
- `SECRET_KEY`: автоматически сгенерированный секрет в Render, одинаковый
  между перезапусками; не сохраняйте его в Git.
- `RITM_COOKIE_SECURE=1`: cookie передаётся только через HTTPS.
- `DATABASE_URL`: адрес PostgreSQL из настроек базы.
- `PORT`: порт, предоставленный платформой; команда Docker его учитывает.

Личный `data/diary.sqlite`, резервные копии и `.dev.vars` исключены из Git и
Docker build. Публичное демо начинается с отдельного пустого дневника.
Демонстрационные графики можно посмотреть кнопкой примера в самом интерфейсе;
кнопка не записывает демонстрационные данные в личную базу.

После успешной публикации проверьте `/api/v1/health`, откройте `/`, добавьте
тестовую запись и перезагрузите страницу в том же браузере. В другом браузере
она не должна появиться. После перезапуска сервиса запись должна сохраниться
в PostgreSQL. Сохраните полученную HTTPS-ссылку в README и отчёте.

## Локальный Docker с прежними записями

Скопируйте всю папку проекта с `data/diary.sqlite`. Остановите старый сервер,
затем запустите:

```sh
docker compose up --build -d
docker compose logs -f
```

Сайт: http://127.0.0.1:5174/. Compose подключает `./data` как каталог данных.
Остановка: `docker compose down`. Эта команда сохраняет записи.

## VPS с Gunicorn nginx и screen

На Ubuntu установите Python, Node.js и nginx, затем из корня проекта:

```sh
npm ci
npm run build:practice
python3 -m venv .venv
.venv/bin/python -m pip install -r backend/requirements.txt
export PUBLIC_DEMO=1
export RITM_DB_FILE=/var/lib/ritm/demo.sqlite
export SECRET_KEY='задайте-длинный-случайный-секрет'
export RITM_ALLOWED_ORIGINS=https://example.com
screen -S ritm
.venv/bin/gunicorn --bind 127.0.0.1:8000 --workers 1 --threads 4 backend.wsgi:app
```

Каталог данных должен существовать и быть доступен пользователю сервиса.
Для выхода из screen без остановки: Ctrl+A, затем D; возврат: `screen -r ritm`.
Остановка Gunicorn: Ctrl+C. Установите конфигурацию из `practice/nginx.conf`,
замените домен и проверьте `sudo nginx -t` перед перезагрузкой nginx.
Для постоянного сервера вместо ручного screen обычно настраивают systemd.
Замените `https://example.com` в RITM_ALLOWED_ORIGINS на фактический адрес
сайта. После включения HTTPS включите `RITM_COOKIE_SECURE=1`.

PostgreSQL нужен, если выбрано сетевое хранилище; достаточно задать DATABASE_URL.
В DBeaver выберите PostgreSQL, укажите host/port/database/user/password из
настроек выбранного сервиса и включите SSL, если этого требует хостинг.
Проверка связи таблиц: SELECT с JOIN из `practice/postgresql_examples.sql`.

## Что уже подтверждено

Наличие `render.yaml` и Dockerfile не означает, что сайт опубликован.
Успешный deploy подтверждается фактическим адресом и проверкой хранения.
